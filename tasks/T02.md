## 구현 순서

1. 승인된 stack의 최소 CLI entrypoint와 application services/ArtifactStore/CanonicalRepository 경계를 구현한다. 기존 코드를 재사용한다.
2. help/version/doctor, data import/show/verify와 automation-safe result/error output을 연결한다. doctor는 secret이나 사용자 문서를 외부로 보내지 않는다.
3. 사용자 원본을 관리 staging에 복사하고 보존 bytes의 SHA-256을 data_id로 삼는다. 신규 acquisition/request는 UUIDv7이며 prepared journal/publish/DB commit/reconcile과 crash failpoint를 구현한다. 사용자 원본을 이동·삭제하거나 과거 bytes/ID/hash를 변경하지 않는다.
4. 새 duplicate request의 거부와 동일 성공 retry의 결과 재생, 명시적 acquisition 다중성, missing file/hash mismatch/path escape를 실제 임시 storage/PostgreSQL 18로 검증한다. 평범한 duplicate import는 acquisition/D2I를 자동 추가하지 않는다.
5. MinerU runtime 미준비는 doctor의 진단으로 표시한다. 파서 구현은 T03이며 여기서 GUI나 graph visualization을 scaffold하지 않는다.

## 현재 사용자 변경 — 이 task에 적용

U01–U03은 이미 적용된 요청이다. CLI-first/GUI-last, PDF parser=MinerU, Artifact Store/Canonical Store/Compiler Runtime을 유지한다. 이 task에서는 GUI를 만들지 않는다. P01–P12는 별도 승인 상태를 확인한다.

U09는 최소 DB/ID/등록 복구 경계를 확정한다. [T02 SQL 초안](../docs/schema/T02_STORAGE_SCHEMA.md)을 실제 선택된 실행 환경·driver/migration runner에 연결했다. 원래 초안/fixture bytes를 보존하고 별도 패키지 migration을 독립 PostgreSQL 18.6/pgvector 0.8.6에 적용했다. I/K/W/P/B·embedding 미래 테이블은 없다. 파일 publish는 DB transaction과 다르므로 같은 request staging 경쟁·같은 hash object 경쟁·crash 복구를 별도 실행했다.

U10: Python 앱을 Docker 기반으로 실행·배포한다. 구체 image/version·dependency lock·CLI/driver/migration runner·독립 DB와 artifact volume profile을 검증한 뒤 T02를 실행한다. 일반 sandbox의 Docker 접근 거부를 전체 engine 접근 불가로 오인하지 말고 ENVIRONMENT의 승인 실행 조회 결과를 확인한다.
